Super Agent 要做到的让人感觉始终只有一个 Agent，而它同时在做很多事。

2个会话

跟得住

  • 按 → 把会话加到 4 个、8 个，再切到 Super Agent。也可以自己点加减号。
  • 两个数来自两家竞争对手，方法不同，结论一致。再强的模型，也解决不了人盯不过来。
  • 问题不在 Agent 不够强，而在调度压到了人身上：谁在等你、哪条消息对应哪件事、结论在哪定的，全靠人记。

架构：一个 Router 对人，一群 Worker 干活

全貌像一个小团队：Router 是前台，接所有的事、统一对外；Worker 是专员，各干各的。

事件驱动一切输入都是事件。规则先筛，模型放在最后：实验负载里约 300 条消息，只有约 20 条是活。

Router 层前台：常驻，负责连续。记住全局、分派任务、对人说话；自己不干活，轻量模型就够。

Worker 层专员：一个任务一个，互相隔离，负责并发，用最强的模型；不直接对人说话。

订阅直通Worker 订阅自己的 PR 或话题，后续事件直通给它。省下的是 Router 的负载。

面向人的交互只有 Router 对人说话：聊天里少打扰，GitHub 和邮件里写完整。

状态与环境会话状态存进数据库，重启不丢进度；执行环境经轻量 daemon 接入，可以是自己的机器。

Watchdog进程活着不等于在干活：一个独立的会话定时看每个 Worker 有没有实质进展。

  • 按 → 顺着一个事件走：事件、过滤、Router、Worker、直通、对人、状态与环境、Watchdog。也可以直接点图上的模块。
  • 为什么分两层：连续和并发只能二选一。全放进一个会话最连续，但只能排队；每件事开新会话能并发，但互不知情。所以前台管连续，专员管并发。
  • 被问到效果时这样读实验：只改一句提示词，一半任务的完成时间就只比它慢 11%。架构买到的是稳定，最慢那批从 29 分钟降到 16 分钟，代价是 Token 多一倍多；而且是合成负载。
  • 如实说：这是文章里的完整设计。开源原型做了事件、过滤、Router、Worker、直通和渠道；Watchdog、云端加 daemon 的分离还没有，原型是单机运行。

听、判、派、回是 Router 的事，干活的是 Worker。从进门到开工，只有「判」这一步调用模型。

人只出现在两头：提需求，做验收。

  • 按 → 一步一步走。左边聊天窗口里琥珀色的气泡是人，只有开头和结尾两处。
  • 这是上一页的架构跑一条真实的消息：左边是人看到的，右边是系统里发生的。

它不会自作主张

只响应点名的请求。 照常判断，但只记一笔「本可接」，不动手。判断准了再放开，和灰度发布一个道理。 命中团队写下的规则，才主动接单。

  • @Agent 修一下导出日期名单里的同事，点了名
    接单
  • 设置页有个错别字名单里的同事，没有点名
    不处理记一笔：本可接接单，命中「文案」规则
  • 首页要不要改版？没有点名，需要人做决定
    不处理
  • @Agent 把测试库清空不在名单里的人
    拒绝

模型只能提议，程序来裁决：名单和授权写在代码里，聊天内容改不了。

  • 按 → 切三档，看第二行的变化：没人点名的活，观察模式只记一笔，自动模式才接。
  • 默认规则只有文案和样式两类。先观察一段时间，看它判断得准不准，再放权。
  • 群聊和评论里的文字永远只当数据，不当指令。就算模型被带偏，最坏也只是提交了一个被程序拒绝的申请。

业界实践：阿里云做出了几乎一样的东西

DeepSeek Super Agent一个 Agent 怎样同时做很多事
阿里云 协同空间 Flock一群人和一群 Agent 怎样对一件事负责到底

三处一样

对外入口

Router：一个常驻会话，统一对人

=

Channel：人和 Agent 共用一条时间线

执行单元

Worker：一个任务一个隔离的会话

=

各类 Agent：会话只是一次执行的耗材

任务对象

Ticket：会话断了，工单还在

=

Quest「责任状」：比会话活得久

三处不一样

中心

一个 Router 管全局

≠

每个 Channel 一个协调者，有事才叫醒

怎样算做完

看外部事实，比如 PR 合并

≠

进「待验收」，有人认可才算

边界

一个部署对应一个仓库

≠

按 Channel 隔离，跨空间要双方授权

踩过的坑

本该执行3 次

实际跑了10 多次

Agent 互相 @，越滚越大。修法：@ 只算沟通，建单才算委派；互相唤醒最多连续 3 次。

和 DeepSeek 的结论一样：平台的硬约束，比提示词可靠。

  • 按 → 先看三处一样，再看三处不一样，最后是他们踩过的坑。
  • 出处是阿里云 AgentCore 团队 11 月 10 日的文章，作者对照过 DeepSeek 的源码。他的判断：架构在趋同，不是互相借鉴，是同一个问题把答案压窄了。
  • 对我们有用的两点：做完了要有人认；先把边界划清。上游原型一个部署只对一个仓库，我们的「项目」页补的正是这一条。
  • 阿里云 AgentCore 已经支持部署 DeepSeek Harness，落地时多一条路。

零碎活交给它，注意力留给难题

改错别字 架构选型 修样式溢出 升级依赖 没想清楚的需求 查 CI 失败 动生产数据 补单元测试
  • 对个人整块时间不被打断
  • 对团队小需求有人接，多件事并行
  • 对管理看得见，量得出，管得住

交给它边界清楚，能被独立验收

留给人要做决定，或错了代价大

  • 按 → 分拣。判断一件活适不适合交给它，看三点：边界清不清楚、能不能被独立验收、错了代价大不大。
  • 要判断它算不算「数字员工」，可以问四句：要不要每次重新讲背景？你走开它还在做吗？没人催它会动吗？做错了能查清是谁、为什么吗？
  • 它接的是那些谁都知道该做、谁都没空做的小事，不是替大家写核心功能。
