架构：一个 Router 对人，一群 Worker 干活

全貌像一个小团队：Router 是前台，接所有的事、统一对外；Worker 是专员，各干各的。

为什么分两层连续和并发难两全：一个会话要排队，多个会话各说各话。所以前台管连续，专员管并发。

事件驱动不用人发起一切输入都是事件。规则先筛，模型最后：实验里约 300 条消息，只有约 20 条是活。

Router 层不用人传话前台：常驻，负责连续。记住全局、分派任务、对人说话；自己不干活，轻量模型就够。

Worker 层不用人盯着专员：一个任务一个，互相隔离，负责并发，用最强的模型；不直接对人说话。

订阅直通不用人传话Worker 订阅自己的 MR 或话题，后续事件直通给它。省下的是 Router 的负载。

面向人的交互少打扰人只有 Router 对人说话，而且只在需要决策或看结果时才打扰。

状态与环境不用人在线会话状态存进数据库，重启不丢进度；执行环境经轻量 daemon 接入自己的机器。

Watchdog不用人在线进程活着不等于在干活：一个独立的会话定时看每个 Worker 有没有实质进展。

  • 按 → 顺着一个事件走。绿色的小标签是这个模块替人拆掉的瓶颈，对应上一页的四行。也可以直接点图上的模块。
  • 为什么分两层：全放进一个会话最连续，但只能排队、互相打断；每件事开新会话能并发，但互不知情。所以前台管连续，专员管并发。
  • 被问到效果时这样读实验：只改一句提示词，一半任务的完成时间就只比它慢 11%。架构买到的是稳定，最慢那批从 29 分钟降到 16 分钟，代价是 Token 多一倍多；而且是合成负载。
  • 如实说：这是文章里的完整设计。开源原型做了事件、过滤、Router、Worker、直通和渠道；Watchdog、云端加 daemon 的分离还没有，原型是单机运行。

人只出现在两头：提需求，做验收。

  • 按 → 一步一步走。左边聊天窗口里琥珀色的气泡是人，只有开头和结尾两处。
  • 每一步下面的小标签是「谁说了算」。模型只提交申请，由一个确定性的核心校验权限、规则和状态；它是唯一能改工单的地方。
  • 好处：模型错了、被带偏了，最坏也只是提交了一个被拒绝的申请。出了事，重启、重放、审计都靠这本账。
  • 「先记账再发」：状态和要做的外部动作记在同一笔账里，提交后再执行，崩溃重启也不会多发或漏发。这是阿里云读源码后的归纳。
  • 如实说：左边的对话是示意，按我们的工具写成了 WeLink 群和 MR。原型目前实际接的是飞书和 GitHub；来源是插件式的，接 WeLink 和公司的代码平台要各写一个来源插件，另有几处通用代码写死了 GitHub，需要一起改。

它不会自作主张

只响应点名的请求。 照常判断，但只记一笔「本可接」，不动手。判断准了再放开，和灰度发布一个道理。 命中团队写下的规则，才主动接单。

  • @Agent 修一下导出日期名单里的同事，点了名
    接单
  • 设置页有个错别字名单里的同事，没有点名
    不处理记一笔：本可接接单，命中「文案」规则
  • 首页要不要改版？没有点名，需要人做决定
    不处理
  • @Agent 把测试库清空不在名单里的人
    拒绝

群聊和评论里的话只当数据，不当指令。名单和授权写在代码里，谁也改不了。

  • 按 → 切三档，看第二行的变化：没人点名的活，观察模式只记一笔，自动模式才接。
  • 默认规则只有文案和样式两类。先观察一段时间，看它判断得准不准，再放权。
  • 优先级从高到低：代码强制、系统提示词、命中的规则、团队约定，最底下才是聊天和评论里的文字。
  • 主动性是最容易翻车的能力，一个乱提 MR 的 Agent 很快会被团队关掉。所以先试运行，判断准了再放开。

项目空间Channel

为什么企业先要边界：上下文和权限不出这个空间。

为什么没事不花模型的钱；中心只管结果。

目标、验收标准、唯一的责任人，都记在账上。

我们的思考：模型之外，落地看工程和组织

一、答案在趋同

DeepSeek阿里云
一个对外的入口因为瓶颈是人的注意力RouterChannel
互相隔离的执行单元因为任务又长又多Worker任务会话
比会话活得久的任务因为活要能追踪、能交接TicketQuest

阿里云对照源码后的判断：不是互相借鉴，是同一个问题把答案压窄了，就像数据库最终都走向预写日志。架构会成为标配，选型不必焦虑。带得走的，是我们自己沉淀的工单、规则和验收标准。

二、Agent 正在回到传统工程

确定性的外壳：都是数据库和分布式系统的老办法

  • 先登记消息不丢，不重复
  • 先记账，再动手崩了能接着做
模型唯一不确定的部件
  • 模型提议，程序裁决被带偏也越不了权
  • 先试运行，再放开主动，但不乱来

「模型是 CPU，Harness 是操作系统和数据库。」模型可以出错，系统要能收敛。评估一个 Agent，别只问模型多强，要问它出错、中断时能不能恢复。模型半年换一代，这层外壳是我们自己的。

三、功课在人这边

改错别字 架构选型 修样式溢出 升级依赖 没想清楚的需求 查 CI 失败 动生产数据 补单元测试
  • 对个人整块时间不被打断
  • 对团队小需求有人接，多件事并行
  • 对管理看得见，量得出，管得住

交给它边界清楚，能被独立验收

留给人要做决定，或错了代价大

阿里云的教训：Agent 跑成功不等于完成，要有人认；只有能被独立验收的工作才分得出去。注意力解放出来之后，新的瓶颈是把活说清楚：目标、验收标准、责任人。这件事模型替不了我们。

单任务看模型，多任务看人的注意力；能不能落地，看工程和组织。

  • 按 → 依次讲三点，最后一下把活分到两边，并收在最后一句上。前两点是阿里云文章结尾的两个趋势，第三点是我们自己的。
  • 趋同：模型已经能把单个任务做完，瓶颈变成注意力，所以要统一入口；任务又长又多，所以要隔离的执行单元；任务要比会话活得久，所以要能追踪的任务对象。我们补的看板，就是让第三样被人看见。
  • 趋同之后，架构不再是谁的优势。产品和模型都可以换，换不走的是我们沉淀在工单里的规则、验收标准和历史。
  • 回到工程：Agent 从一次对话变成长期运行的进程，就要面对老问题。进程会崩、机器会离线、消息会重复、副作用不能执行两次。可靠性不只看模型能不能做对，还看做错或中断时能不能恢复。
  • 功课在人这边：只有能被独立验收的工作才能分出去。验收标准就是任务的接口，这件事模型替不了我们。先从观察模式开始，用一次交付率和打扰次数说话。
  • 最后一句是在 DeepSeek 那句话后面接的半句：单任务的上限看模型，多任务的上限看人的注意力；而能不能落地，看的是工程和组织。
